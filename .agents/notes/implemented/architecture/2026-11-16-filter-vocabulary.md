# Agent Note: 频道筛选词表与豆瓣冷门组合的读取

Status: implemented

## Problem

每个频道需要像主流视频应用一样细的筛选（类型、地区、年份）。豆瓣 `recommend` 自带的 `recommend_categories` 每个频道只有十来个类型；未知标签不报错而是返回空列表，所以词表里的词必须逐个证明有内容。另外实测发现豆瓣对近期没人访问过的筛选组合是现算的：要么把请求挂到算完（实测最长约 14 秒），要么约 1.2 秒后返回“部分页”——`total` 正确，条目却只有几条甚至 0 条，而且同一请求可重复返回同一部分页一分钟以上。把部分页当成结果会让列表提前结束或漏片。

## Decision

- 词表（[taxonomy.ts](../../../../src/main/data/taxonomy.ts)）：类型用豆瓣标签，地区用豆瓣的国家/地区标签加“华语”“欧美”两个语言组，年份用单年标签（2010 至今）加年代标签和“更早”。动画、纪录片同时读电视与电影两条列表并合并。`tags=a,b,c` 为交集，由豆瓣服务端过滤。
- 准入规则为 `npm run probe:filters` 用生产数据源逐项读取首页，至少返回 6 部。更新后于 2026-11-20 21:38 重放，736 项全部通过。[线上探测](../../../../docs/evidence/filter-vocabulary.json)与[单测](../../../../tests/data.test.ts)逐项校验词表。
- 冷门组合（[douban.ts](../../../../src/main/data/douban.ts) 的 `listing`）：列表请求单次等待 20 秒且超时不重发（重发会让豆瓣重新计算）；返回条数少于 `min(count, total-start)` 即判为部分页，不缓存，0.8 秒后重读一次；仍不完整就把这一页拆成更小的页（30 → 10 → 5）读，小页先完成而且条目与顺序一致。仍读不全时报 `TIMEOUT`，界面显示“连接超时，请重试”。

## Alternatives considered

- 只用豆瓣自带的十来个分类：达不到要求的细分程度。
- 以详情页的 genres/tags 在本地二次过滤：一页 30 条过滤后常常所剩无几，分页与总数都失真；服务端标签交集已经准确。
- 换 TMDB / TVmaze 做筛选：前者需要独立凭据，后者华语内容覆盖不足，而且条目身份要和豆瓣详情、片源匹配重新对齐。
- 公益反代实例（LunaTV、LibreTV 等公开配置）：多一个故障点和限流，数据仍来自同一个豆瓣接口。
- “同一部分页连续出现两次就当作真实结果”：实测部分页可以稳定重复，这条规则会把 1/24 的页面当成全部内容。
- 部分页直接展示并继续翻页：缺的不是最后几条而是任意几条，后续页不会补回来。

## Consequences

冷门筛选首次打开可能等到十几秒，之后 10 分钟内走缓存。单测时长因限速器约 15 秒。豆瓣新增或下线标签时需重跑 `npm run probe:filters` 并同步词表，否则证据一致性单测失败。年份列表按当前年份生成，跨年后同样需要重跑。
