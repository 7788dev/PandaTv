# Agent Note: 媒体代理放行的端口

Status: implemented

## Problem

媒体代理（[network.ts](../../../../src/main/playback/network.ts)）原先只允许 80 和 443 端口。实测金鹰资源的分片在 `c.baisiweiting.com:18443`，飘零资源也有线路使用高位端口：这些线路的清单能读到，分片请求全部被拒。金鹰是部分新片的唯一片源，结果是“片源暂时无法连接”。

## Decision

`allowedPort`：与浏览器一致——1–65535 中不在 Fetch 标准“坏端口”清单内的端口都放行，清单内的端口（邮件、SSH、DNS、IRC、SIP、X11、NFS 等）继续拒绝。公网地址校验、重定向逐跳校验与 DNS 固定（见 [DNS 记录](2026-11-16-safe-proxy-dns.md)）不变。

2026-11-17 修订：最初只放行 80、443 和 1024 以上的非清单端口。在国内服务器上实测红牛资源的分片在 `hnts.ymuuy.com:65`，65 不在坏端口清单内、浏览器照常播放，却被“1024 以下一律拒绝”挡住，于是改为直接采用整份清单。

## Alternatives considered

- 维持 80/443：比浏览器更严，却没有对应的安全收益——同一条 HLS 在任何浏览器里都能播；代价是整条片源不可用。
- 为每个源配置允许的端口：CDN 主机与端口都在轮换（见去广告复审里域名名单失效的教训），名单会很快过期。
- 1024 以下只放行 80/443（第一版）：比浏览器严，挡掉了红牛资源在 65 端口的分片，没有换来安全收益——坏端口清单已经覆盖了低位的危险服务。
- 放行全部端口：允许向公网主机的邮件、SSH 等服务端口发请求，超出浏览器自身的边界。

## Consequences

播放源数据仍是不可信输入，能触达的范围与浏览器发起 GET 请求相同。回归用例在 [playback.test.ts](../../../../tests/playback.test.ts)（拒绝 22、25、993、5060、6667、10080，放行 65、8080、18443）；经本地代理读取金鹰清单、密钥与分片的实测见[播放审阅](../../../../docs/playback-audit.md)。
