# Agent Note: 冷启动先显示上次的内容，连接卡住时尽早换一条

Status: implemented

## Problem

完全退出后再打开，首页要等几秒才出数据和海报；第二次打开明显好一些。实测原因不是初始化，而是网络上的偶发停顿叠在“等全部答复”的做法上：

- 首页由 10 个上游答复拼成，多数 0.2–0.6 秒，但任何一个都可能偶尔花几秒（2026-11-16 实测三次读取内最长 4 秒，出现过一次 9 秒）；等齐了才显示，页面就和最慢的那个一样慢。
- 本机代理下，新连接偶尔 TCP 立即接通而 TLS 握手永远不完成（约百分之一），只能等整个请求超时：一张海报或一个列表 6–10 秒。
- 公共 DNS（DoH）的一次查询偶尔挂到超时，一个图片域名下的海报全部多等 4 秒。
- 海报每次启动都重新下载。

## Decision

- 首页（[douban.ts](../../../../src/main/data/douban.ts)）：读过的首页立即用上次的答复显示，后台再读，内容不同才替换；新读取失败时保留并告知“正在显示已保存的信息”。没有保存过时先给页首（主推与第一栏），其余栏目按页面顺序随答复到达。保存的只是豆瓣上次的真实答复，不是替代数据。
- 海报落盘（[proxy.ts](../../../../src/main/playback/proxy.ts)）：下次启动直接从磁盘给；目录的清理推迟到首页显示之后。
- 握手期限（[handshake.ts](../../../../src/main/handshake.ts)、[transport.ts](../../../../src/main/data/transport.ts)）：新连接在期限内没完成握手就断开重连（数据请求 1.5 秒，再试 4 秒；海报按次递增），刚卡住的地址 30 秒内排到后面。握手正常只要 0.1–0.5 秒。
- DNS（[network.ts](../../../../src/main/playback/network.ts)）：第一个解析器 350 毫秒没答复就同时问第二个，各等不超过 1.5 秒；都没答复才耐心再问一轮。解析结果不是公开地址时不回退。

实测（打包后的 `release/win-unpacked/Panda.exe`，2026-11-17 15:59，`npm run probe:startup` 24 次全新启动 + 4 次再次启动，[startup-timing.json](../../../../docs/evidence/startup-timing.json)，进程创建后的毫秒数）：全新启动骨架 349、页首内容 702（最慢 1007）、可见海报 1345（最慢 3071）、整页 1754（最慢 2865）；再次启动页首与整页 526、可见海报 669（最慢 842）。28 次启动没有一次失败或停顿数秒。

## Alternatives considered

- 加一个启动画面：只是把等待换个样子，原型里也没有这一屏。
- 首次启动用内置的示例首页垫底：违反“不显示假数据”。
- 只加长或缩短整体超时：停顿发生在握手阶段，缩短整体超时会误杀正常的慢答复，加长则更卡。
- 启动时预热所有连接：卡住的是偶发的个别连接，预热不能避免，只是把同样的等待提前。
- 回退到系统 DNS 给的保留地址：那是本机代理的映射地址，[safe-proxy-dns](2026-11-16-safe-proxy-dns.md) 已说明不能连。

## Consequences

再次启动先看到的是上次的首页，约一两秒内被新内容替换（内容相同则不动）。海报目录占用磁盘，启动后清理。停顿是偶发的，几次干净的启动说明不了问题：动过首页、海报代理、连接处理或主进程启动后，按 AGENTS.md 跑 `npm run probe:startup`，全新启动不少于 20 次。
